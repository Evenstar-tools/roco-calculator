## 处理规则

1. 低于预警：正常构建，不把几十或几百字节的变化作为阻断项。
2. 超过预警但未超过硬上限：记录优化待办，检查新增依赖、重复资源和入口静态依赖；不反复要求用户批准微小扩容，不单凭此项停止交付。
3. 超过硬上限：阻断发布，先用 `node scripts/build-attribution.mjs` 定位增长；优先去重、按需加载或分离数据。只有确有新业务规模且有性能证据时再重新讨论预算，不能直接跟随产物增加。
4. 大依赖、框架升级、入口加载方式变化或出现卡顿投诉时，除体积外复测真实加载和交互；不等待碰到大小上限才处理体验退化。

## 大小影响什么

- 网络：未缓存资源越大，首次访问及更新后需要下载的字节通常越多，弱网影响更明显。实际传输还取决于服务器 gzip／Brotli、缓存、连接与延迟。
- JS：压缩包下载后仍要解压、解析、编译和执行；低端手机可能出现启动慢、输入或点击响应迟缓。原始大小用于补充观察，不等于运行内存或执行耗时。
- CSS：需要下载和解析，关键样式会影响首次绘制；样式计算成本还取决于选择器及 DOM，不能仅凭 KiB 推断耗时。
- 资源与数据：增加安装、缓存及存储占用；JSON 还需要解析并建立运行时对象。客户端目录总量不等于用户首屏流量。
- 不会因为把预算数字调大就改变伤害计算精度，也不会自动让程序变大或变快；变的是发布检查标准。

以理想有效带宽 1 Mbps 粗算，增加 100 KiB 传输约多 0.82 秒，未包含连接延迟、缓存和执行耗时。之前 0.1 KiB 级差异约百字节，不是可感知性能突然退化的证据。

## 不只看体积

现有打包归因报告显示当前入口静态依赖约 297.60 KiB gzip，全部 JS 合计 348.40 KiB，两者不是同一口径。前者排除动态依赖，不是实际浏览器网络测量；也不含运行数据、图片等首屏资源。Service Worker 预缓存应用壳和 HTML 引用的资源，其余按请求缓存，因此总目录 15.82 MiB 不能当成每次打开都要下载的流量。

现有冷启动／热启动／技能搜索 E2E（10 秒／5 秒／1.5 秒）已加入日常发布验收。这些较宽阈值用于捕捉本地严重回归，不代表真实用户或弱网达标。后续真实用户性能评估应参考第 75 百分位 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1；当前没有本轮现场数据，不能声称已满足这些指标。
